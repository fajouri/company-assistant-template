# Architecture
A modular ASP.NET Core application serves compiled React assets and APIs from one origin.
PostgreSQL/pgvector stores approved policy documents, their versions and chunk embeddings.
Later introduce Application and Infrastructure projects when actual use cases require those boundaries; do not add empty layers.
Ingestion runs as a separate command (`migrate`/`ingest`), not during chat. A separate private MCP service will expose narrow read-only tools.
Entra authentication terminates in the backend through Microsoft.Identity.Web 4.16.1 using the authorization-code flow with PKCE. OIDC tokens are not persisted into the cookie or returned to React; the cookie authentication ticket contains identity claims rather than raw OIDC tokens. The session cookie is HTTP-only, Secure and SameSite=Lax. Logout is a POST protected by double-submit antiforgery validation. See [identity setup](identity.md).
Authorization uses validated Entra `tid`/`oid` claims and explicit app-role-to-permission mappings. `Employee` grants `assistant.use`, `HR` grants `hr.data.read`, and `TechnicalAdmin` grants `technical.administration`; roles do not inherit from one another. The default authenticated policy requires a recognized assignment, and sensitive endpoints add named permission policies. Authorization precedes retrieval and tool execution; a future MCP service must independently validate delegated identity and permissions.
Only approved, currently effective documents are searchable. Personal HR records remain outside general retrieval. Document metadata (`id`, `title`, `owner`, `approver`, `version`, `effective_date`, `approval_state`, `review_date`, `access_policy`) comes from validated Markdown front-matter. The retrieval store enforces `deleted_at IS NULL`, `approval_state = 'approved'`, `effective_date <= CURRENT_DATE` and `access_policy` membership inside the SQL `WHERE` clause before vector ranking (`ORDER BY embedding <=> $query`) and `LIMIT`. Access policies map `assistant.use` to `employee` and `hr.data.read` to `hr`; the application supplies trusted permissions, never model parameters.
Chat uses the Semantic Kernel chat abstraction (`Microsoft.SemanticKernel.Core`) over a configurable Foundry/Azure-OpenAI-compatible deployment. Each request is deterministic: authorize the `assistant.use` caller, retrieve their ACL-filtered passages, run one bounded model generation, and return NDJSON after checking citation numbers against retrieved passages (chunk/document/version ids). This check does not prove semantic support. Document passages are injected as untrusted data in a user message, never into the system instruction. Conversation state is in-process and bounded; raw conversation content is not persisted by default. There is no multi-agent planning and no managed agent service.

OpenTelemetry exports metadata without prompts or personal tool results by default.
